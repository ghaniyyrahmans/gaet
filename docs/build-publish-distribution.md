# Build, Publish & Distribution

This is the operating reference for releasing gaet: CLI binaries, GitHub Release
assets, and the npm SDK. **The git tag is the only source of truth for a version.**
Everything else is derived from it or pinned in one place.

---

## 1. Where a version comes from

| Surface | Source | Manual edit on release |
|:---|:---|:---|
| CLI binary version | git tag injected via linker flags | none |
| `go install module/cmd@version` | Go module build info | none |
| Dashboard version badge | `/api/status` response field `version` | none |
| GitHub Release assets | git tag | none |
| npm SDK version | git tag, synced into `sdk/package.json` by the workflow | none |
| Installer download pin | `GAET_VERSION` (`install.sh`) / `$GaetVersion` (`install.ps1`) | **2 lines** |
| Documentation URLs | stable `releases/latest/download` asset URL | none |

The two installer variables are the only version literals that are intended to
be edited by a human. `sandbox/verify-docs.sh` (check 9) keeps them in sync.

---

## 2. How the binary reports its version

`core.Version` in `pkg/core/paths.go` is a `var`, not a `const`, specifically so
the linker can replace it:

- **Release builds:** `.github/workflows/release.yml` injects
  `-X github.com/ghaniyyrahmans/gaet/pkg/core.Version=<version>` from the tag for
  every platform.
- **`go install .../cmd/gaet@vX.Y.Z`:** Go stores the module version inside the
  binary. `debug.ReadBuildInfo()` in the `core` package `init()` reads it back.
- **Plain `go build`:** neither mechanism applies, so the value stays `"dev"`.

`cmd/gaet/main.go` prints this value for `--version`. The embedded dashboard
does not hardcode a version: `handleStatus` adds `"version": core.Version` to
`/api/status`, and the page fills its version badge from that field.

Installer URLs are built from `core.InstallerBase`, a stable version-free base
pointing at `releases/latest/download`. Do not put `main` or a tag into that
constant or into `cmd/gaet/main.go`.

## 3. GitHub Release pipeline

Workflow: [release.yml](../.github/workflows/release.yml)

- Trigger: `push` of a tag matching `v*`.
- The tag must be numeric (`vMAJOR.MINOR.PATCH`); non-numeric tags fail the
  build steps deliberately.
- Linux: `gaet-linux-<arch>.tar.gz` plus `deb`, `rpm`, `apk`, and Arch packages
  generated by nfpm.
- Windows: portable `gaet-windows-amd64.exe` and WiX-built `.msi`.
- macOS: `gaet-darwin-<arch>.tar.gz` and unsigned `.pkg` installers.
- `finalize` copies `install.sh` and `install.ps1` into `dist/`, writes one
  `checksums.txt` over every asset (installers included), and publishes the
  release with generated release notes.

---

## 4. npm / SDK pipeline

Workflow: [npm-publish.yml](../.github/workflows/npm-publish.yml)

- Triggers: `push` of `v*`, `release: published`, and `workflow_dispatch` with an
  explicit `version` input for retries.
- The `push` trigger is primary: a release created with the built-in
  `GITHUB_TOKEN` does not trigger other workflows, so waiting for the `release`
  event alone is unreliable. One tag push runs the binary and SDK pipelines.
- Version resolution: dispatch input if given, otherwise `GITHUB_REF_NAME` with
  the leading `v` removed. The value must be numeric `X.Y.Z`.
- `npm version <version> --no-git-tag-version --allow-same-version` runs inside
  `sdk/`, updating `sdk/package.json` and `sdk/package-lock.json` **in the
  runner**. The committed copies may therefore lag until the next version-bump
  commit; the published artifact is always correct.
- Steps: `npm ci` → `npm run build` → `npm test`. `sdk/dist/` is generated here
  and gitignored; it is not committed.
- An `npm view` guard skips publishing when that version already exists, making
  a re-pushed tag harmless.
- Publishing uses `npm stage publish --access public` with npm Trusted Publishing
  (OIDC, `id-token: write`, no `NODE_AUTH_TOKEN`). A staged publish needs
  maintainer approval in npm before it goes live. Changing the workflow filename
  requires updating the trusted publisher configuration on npmjs.com.

## 5. Quick install

- Bash: `curl -sSL https://github.com/ghaniyyrahmans/gaet/releases/latest/download/install.sh | bash`
- PowerShell: `irm https://github.com/ghaniyyrahmans/gaet/releases/latest/download/install.ps1 | iex`

The one-liner fetches the installer from the latest published GitHub Release, not
from a development branch. GitHub resolves `latest` to the newest non-draft,
non-prerelease release, and the asset is immutable once published. GitHub orders
by publication time, not by the highest tag number, so always flag prereleases as
such. The installer itself pins *which release* it downloads through its single
version variable, so the script stays reproducible without pinning the URL itself.

User documentation site: <https://gaet.ghaniyyirrahmans.me/>

## 6. Release checklist

1. Update `GAET_VERSION` in `install.sh` and `$GaetVersion` in `install.ps1` to
   the new numeric version. These should be the only version edits.
2. Commit the change, then create and push the tag:
   `git tag vX.Y.Z && git push origin vX.Y.Z`
3. Confirm `release.yml` produced assets with checksums, and `npm-publish.yml`
   built and staged the SDK. Both start from the same tag push.
4. Approve the staged npm release in the npm UI.
5. Run `bash sandbox/verify-docs.sh`; it must end with `EXIT: 0`.

Do not hand-edit `core.Version`, the dashboard badge, `core.InstallerBase`,
`cmd/gaet/main.go`, or version numbers in the docs during a release.

---

## 7. Guardrails

`sandbox/verify-docs.sh` check 9 verifies:

- `sdk/package.json` and `sdk/package-lock.json` agree;
- the two installer version pins agree;
- `core.InstallerBase` points at `releases/latest/download`, not `main` or a tag;
- `cmd/gaet/main.go` contains no hard-coded installer URL;
- live docs contain no `raw.githubusercontent.com` or `main/install` URL.

Branch policy (including LTS branches) is described in [AGENTS.md](../AGENTS.md).
For command-level documentation, see the [documentation index](README.md).
